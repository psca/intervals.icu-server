Design Review

Google Login for Remote MCP Auth

Add Google login while keeping GitHub, using provider-scoped accounts and a normal choice screen.

Cloudflare Worker GitHub + Google No legacy migration
GH
G
Goal

Give non-technical users a familiar login path

  • Keep GitHub login for existing developer-oriented usage.
  • Add Google login for a more common consumer UX.
  • Collect intervals.icu athlete ID and API key after OAuth login.
  • Do not migrate existing credentials; current users will re-auth and re-enter intervals.icu credentials once.
The auth change is only for remote Worker mode. Local stdio mode stays unchanged.
Current State

GitHub is wired directly into the login flow

/authorizeParse MCP OAuth request and redirect straight to GitHub.
/callbackExchange GitHub code and read GitHub username.
/configureCollect intervals.icu credentials for first-time users.
/mcpUse OAuthProvider props to load encrypted credentials.
Credentials are currently keyed as credentials:<github_username>, and encryption also uses that username as context.
Account Model

Provider plus stable subject is the canonical user id

<provider>:<stable-subject>

github:12345678
google:108765432109876543210

Used for

  • OAuthProvider userId
  • Token props
  • Credentials KV keys
  • Settings sessions
  • Encryption context

Not used for identity

  • Email address
  • GitHub login name
  • Display name
  • Any cross-provider match
Identity Abstraction

Replace GitHub-only helpers with provider implementations

type AuthProvider = "github" | "google";

interface AuthIdentity {
  provider: AuthProvider;
  subject: string;
  displayName: string;
  email?: string;
  emailVerified?: boolean;
}
  • GitHub subject: stable numeric id; display name: login.
  • Google subject: OIDC sub; scopes: openid email profile.
  • Email can be displayed only when verified, never used as the key.
Provider Choice

Both OAuth entry points start with a choice screen

MCP authorization

  1. /authorize parses MCP OAuth request.
  2. Store oauth_state:<id>.
  3. Render GitHub and Google buttons.
  4. /login validates state and redirects to selected provider.

Settings login

  1. /settings creates settings_state:<id>.
  2. Render the same provider buttons.
  3. /login records selected provider in state.
  4. Provider redirects back to shared /callback.
The callback must read the provider from KV state. It must not trust provider query parameters.
Callback

One callback handles both providers and both flows

  1. Read code and state.
  2. Check oauth_state:<state>, then settings_state:<state>.
  3. Read selected provider from the validated state record.
  4. Exchange the code and resolve AuthIdentity.
  5. Compute accountId.

Returning user

Credentials exist, so call completeAuthorization with canonical userId and props.

First-time user

No credentials, so store identity in configure_state and redirect to /configure.

Credentials

Everything keys off the canonical account id

credentials:<accountId>

credentials:github:12345678
credentials:google:108765432109876543210
  • /configure stores encrypted intervals.icu credentials under this key.
  • /settings/save updates the same provider-scoped key.
  • /settings/disconnect deletes this key and revokes grants for the same account id.
  • apiHandler reads credentials using ctx.props.accountId.
No Legacy Migration

Existing records are intentionally left behind

  • Old keys like credentials:<github_login> are ignored.
  • Current users re-authenticate and re-enter intervals.icu credentials.
  • Old OAuth grants may remain until expiry or manual cleanup.
  • The implementation avoids decrypt-old-key and re-encrypt-new-key migration logic.
This keeps the account model uniform from day one of Google support.
Configuration

Add Google OAuth configuration beside GitHub

Existing

GITHUB_CLIENT_ID
GITHUB_CLIENT_SECRET

New

GOOGLE_CLIENT_ID
GOOGLE_CLIENT_SECRET

The Google OAuth web client redirect URI is https://<worker-host>/callback.

Security

Security decisions to preserve in implementation

  • No automatic cross-provider account linking by email.
  • No GitHub login as the canonical subject.
  • No provider value trusted from callback query parameters.
  • Short-lived state records for OAuth, settings, and configure flows.
  • HTML-escape display name, email, and athlete ID before rendering.
  • Use Google userinfo first; validate ID tokens fully if introduced later.
Testing

Coverage should follow the identity boundary

Auth helpers

  • GitHub URL and stable id identity
  • Google URL scopes and userinfo identity
  • Canonical accountId construction

Worker flows

  • Provider choice and state validation
  • Callback reads provider from KV
  • Configure, settings, disconnect, and MCP lookup use accountId
Docs

README and AGENTS need the new operating model

  • Remote auth supports GitHub or Google.
  • Users are separate per provider.
  • Existing pre-Google credentials are not migrated.
  • GitHub and Google OAuth setup instructions are both documented.
  • GOOGLE_CLIENT_ID and GOOGLE_CLIENT_SECRET are documented.
Out of Scope

Keep this release focused

No email auto-linking No manual account linking No legacy credential migration No stdio changes

The narrow target is a clean multi-provider login layer for the remote Worker.

Decision Summary

Recommended implementation path

  1. Add provider abstraction and canonical account id helpers.
  2. Add provider choice for /authorize and /settings.
  3. Use GitHub numeric id and Google OIDC sub as subjects.
  4. Store credentials under credentials:<accountId> and use the same account id for OAuth grants.
  5. Update tests, docs, and Cloudflare configuration.
Review question: does this scope match what you want for the first Google-login release?
